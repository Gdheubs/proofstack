## Still-open source risks

### S-01 — Signed upload ingress is not bounded (P1; SEC-01)

**Source update (2026-10-21):** signed PUT URLs were removed. Browsers upload to the authenticated, CSRF-protected, rate-limited same-origin API, which refuses declared bodies over 8 MiB unread, caps streamed bodies at 8 MiB, and checks declared size, type and signature before writing to R2 (`routes/community.ts`, `services/community-assets.ts`; `tests/asset-upload-route.test.ts`, `tests/community-assets.test.ts`). Remaining: live R2 acceptance and a per-account byte budget; the 100-row cap still bounds count, not bytes. The original evidence below describes the removed Replit adapter.

**Evidence:** `API/services/community-assets.ts:31-85` accepts a declared size/type and counts asset rows. `API/lib/objectStorage.ts:128-147,249-275` signs a 900-second PUT using only bucket, object name, method and expiry. Actual size is checked later at completion (`community-assets.ts:201-212`). The direct cloud body bypasses API JSON/rate limits.

**Risk:** Oversized/repeated/abandoned writes can consume provider capacity before rejection; live-object/version byte accounting is not provided by a 100-row cap. Actual sidecar constraints were not inspected, so this is a missing enforced contract in source, not a measured provider exploit.

**Smallest safe fix / exit:** Introduce a bounded authenticated streaming boundary (bytes, concurrency, deadline, disconnect handling) or a provider-supported policy proven to enforce these limits at ingress. Reserve byte capacity atomically and account for outstanding capabilities/versions. Test dishonest declarations, absent/chunked length, oversize, replay and no-completion. Authorized disposable-provider acceptance must show rejection before accepting the entire excessive body, not merely completion failure. Do not remove uploads or silently claim them supported; any temporary issuance restriction needs an explicit owner-approved release scope and must preserve authorized existing reads.

### S-02 — Image validation is only a signature check (P1; SEC-02)

**Source update (2026-10-21):** uploads are now fully decoded and re-encoded with `sharp` 0.35.5 before the R2 write (`services/image-canonical.ts`). The header is inspected first, so declared-type mismatches, more than 8,192 pixels per side, more than 25 megapixels (including header-only decompression bombs) and animation are rejected before decoding; decoding uses sharp's pixel limit as a backstop, `failOn: warning` (truncated/corrupt files fail) and a 20-second timeout; output carries no EXIF/XMP/ICC metadata; decodes are serialized with a bounded queue and run without holding the asset row lock. Real-image tests: `tests/image-canonical.test.ts`. Remaining: decoding runs inside the API process rather than an isolated worker, so a libvips vulnerability would affect the API; memory per decode is bounded by the pixel cap (about 100 MB at 25 MP RGBA) on a 512 MB instance.

**Evidence:** `API/services/community-assets.ts:38-48,192-225` downloads at most the initial header range, checks metadata/magic bytes, and copies original bytes to ready storage. There is no complete decoder, dimension/pixel/frame cap or canonical re-encode on this path.

**Smallest safe fix / exit:** After bounded ingress, constrain a decoder worker by compressed bytes, dimensions/pixels, frames, memory and time; strip metadata and promote only a supported canonical output. Preserve existing PNG/JPEG/WebP product support; define animation handling explicitly. Reject header-only/truncated files, corrupt images and resource bombs, and prove failures never activate a ready reference. CSP/MIME checks remain useful but do not replace decoding.

### S-03 — Promotion, abandoned uploads and pre-enqueue location lack durable lifecycle (P1; SEC-04)

**Source update (2026-10-21):** there is no quarantine copy or promotion step; the final immutable `ready/` key is reserved in SQL before any write and is the only key cleanup ever targets. Still open: abandoned `pending` reservations keep quota until deleted, a crash between the R2 write and commit leaves an object at the reserved key, and namespace rotation before enqueue. The evidence below describes the removed adapter.

**Evidence:** `API/services/community-assets.ts:190-227` chooses a fresh random destination, copies and sets ACL before SQL update/audit/commit. No durable promotion destination exists before external I/O. Expired completion returns `UPLOAD_EXPIRED` without expiring the SQL reservation. `DB/community-assets.ts:14-24` stores a relative path, not upload-time bucket/namespace. Resolution uses current configuration (`API/lib/objectStorage.ts:150-173`); deletion captures the current namespace only at enqueue (`community-assets.ts:150-175`). Account FK cascade deletes rows, not unqueued objects.

**Risk:** Rollback/crash can orphan ready copies; successful promotion leaves quarantine bytes; abandoned reservations persist; namespace rotation before enqueue can resolve an old relative path in the wrong namespace. The deletion outbox fixes none of these earlier lifecycle stages.

**Smallest safe fix / exit:** Extend the existing durable lifecycle approach, not a new queue platform: persist canonical upload-time location, capacity reservation, capability expiry, stable promotion destination and state **before** external copy; activate only verified output, and reconcile failed/abandoned attempts. Delay final staging cleanup until PUT expiry plus grace and handle retained versions explicitly. Require reviewed mapping/backfill before namespace rotation. Test crashes around copy/ACL/SQL/audit/commit, duplicate completion, late PUT recreation, and account cascades. Inventory existing orphans read-only first; never delete by prefix/age alone or compensate for an unknown commit outcome.

### S-04 — Git allocation/cascade/GC lifecycle is missing (P1 when Git enabled; SEC-05)

**Evidence:** `API/services/repositories.ts:211-254` creates the UUID directory and Git objects before inserting metadata; its owner quota counts live repository rows. `repositories.ts:325-345` and `API/services/pull-actions.ts:257-306` write objects before final quota check/SQL/audit. `API/services/community-project-actions.ts:97-110` and `community-org-actions.ts:50-76` delete parent SQL rows without a filesystem tombstone; `DB/repositories.ts:19-21` cascades repositories. `API/services/repository-git.ts:81-87` disables auto-GC. Searches of the service inventory found no durable repository cleanup/promotion registry.

**Risk:** Failed creation and successful parent deletion can leave bytes while releasing row quota; failed writes leave unreachable objects. Source quota checks are not global disk/inode accounting.

**Smallest safe fix / exit:** Add durable allocation/capacity reservation before mkdir and capture owner/UUID/storage target tombstones before every cascade. Cleanup must survive the deleted rows, validate canonical UUID paths, reject symlinks, coordinate exclusion with readers/writers and quarantine before delayed removal. Release capacity only after acknowledged cleanup. Treat GC as separate reviewed work: protect SQL branches, releases **and retained PR history heads**, with exclusion and retention. Test rollback, crash/retry, fill/delete cycles, concurrent clone/commit and full retained-ref restore. No blind `git gc --prune=now`, unregistered-directory removal or live repair is authorized. Storage provisioning is separately D-01.

### S-05 — Recovery and clone credentials do not share a complete security-event policy (P1; SEC-11)

**Evidence:** `API/services/auth-mfa.ts:183-193` removes a verified native factor and revokes sessions but does not invalidate app recovery codes; codes are replaced on explicit regeneration (`209-235`) and deleted only after successful recovery factor deletion (`288-315`). `recover-mfa` commits used-code/lockdown/session revocation before external factor deletion (`251-294`) with no durable per-factor progress or repair job. `API/services/auth-account.ts:129-151` changes account role/status and revokes sessions only. `API/services/repositories.ts:356-373` rejects disabled/recovery-locked users but does not permanently revoke their clone tokens. Source search found token revocation only in the explicit repository-token action (`278-283`).

**Risk:** Old app recovery codes can survive factor removal/re-enrollment; interrupted native reset leaves partial progress to manual handling; a still-unexpired clone token can become usable after reactivation/recovery clearance if repository access is again allowed. These are lifecycle gaps, not proof that a recovery code grants native AAL2.

**Smallest safe fix / exit:** Define explicit credential-epoch or transactional revocation policy for verified-factor removal/replacement, recovery start and security disable. Invalidate affected recovery/clone credentials durably; require deliberate renewal rather than status-clear resurrection. Persist external reset intent/progress with idempotent retry/reconciliation and fail-closed account state until verified native completion. Also cover unenroll success followed by audit/revocation failure: SQL cannot undo the provider operation. Keep primary verification/native assurance guards intact. Add independent native code-use races, old-code-after-reenroll, partial factor-reset/restart, disable/reactivate and recovery/clear token tests; stage real provider failures separately. Current `mfaAction` characterization tests are not closure evidence.

### S-06 — Selected-provider lifecycle and first operator are incomplete (P1; SEC-08/09)

**Evidence:** `API/services/auth-provider.ts:121-143` advertises Firebase factor enrollment/recovery as unavailable; `API/services/auth-actions.ts:39-61` rejects unsupported actions; `API/services/auth-account.ts:195-197` requires Supabase for target-native-factor role assignment. `OPS/bootstrap-admin.mjs:5-8,38-74` is development-only and Supabase-specific.

**Smallest safe fix / exit:** Complete the selected provider's required native factor/recovery and audited first-operator workflow; keep unsupported operations visibly fail closed. Do not change `NODE_ENV` to run development bootstrap in production. Provider cutover needs explicit verified identity linking that preserves app ownership and revokes old credentials, not email-only linking. Live domain/OAuth/MFA/revocation/privileged-role acceptance remains D-02. No provider switch or role grant was attempted.

### S-07 — Provider I/O retains SQL transactions (P1 under Supabase load; SEC-10)

**Evidence:** `API/services/auth-sessions.ts:397-489` holds the session row transaction through `sessionClient`/`getUser`; `auth-account.ts:199-280` and `community-org-actions.ts:108-131` perform target-factor I/O within mutation transactions. `lib/db/src/index.ts:13-23` caps each pool at ten clients.

**Smallest safe fix / exit:** Move bounded provider I/O outside the lock only with credential/version fencing and post-I/O session/user/revocation rechecks. Preserve refresh-token concurrency correctness. Test independent native parallel refresh, stale responses, revoke/disable during I/O and pool saturation/provider outage. Do not replace native verification with a stale identity cache. Provider timeout behavior and production pool budget need D-02/D-04 acceptance.

### S-08 — Whole-account privacy, publication and retention lifecycle is incomplete (P1 for real-user launch; SEC-21)

**Evidence:** `API/routes/index.ts:19-27`, the route inventory and complete `API/services/auth-input.ts:38-151` expose no whole-account export/erasure request workflow; `auth-account.ts:87-153` provides status management, not erasure. `DB/community-assets.ts:15-17` and `DB/repositories.ts:19-21` demonstrate why SQL cascades alone cannot erase bytes. `API/services/assessments.ts:143-154` exposes completed results for an active published handle, without per-result publication policy. `API/routes/auth.ts:69` invokes traffic-triggered `auth-cleanup.ts:3-20`; this is not a complete retention scheduler.

**Smallest safe fix / exit:** Approve a data-family/purpose/retention/publication/hold inventory, then implement fresh-assurance export and durable deletion requests with requester isolation, organization last-owner transfer, provider/session/clone revocation and external-store completion. Exclude raw credentials from exports. Explicitly resolve assessment publication choice and user-facing disclosure. Retention must run independently of user traffic with bounded batches; deletion requests must survive backup restore/replay. Test two-user isolation, last owner, replay, crash/retry, provider failures and retained-audit minimization. Legal applicability and vendor terms require qualified owner review; this register makes no compliance certification.

### S-09 — Direct AI assist has different spending/disclosure controls (P1 when enabled; SEC-17)

**Evidence:** `API/services/community-ai.ts:10-49` sends supplied text to a configured external provider using a fallback model, without a shared global reservation ledger or explicit consent field on this path. Timeout and `maxRetries: 0` are positive controls, not spending/retention policy. `OPS/preflight.mjs:98-110` conditions its HTTPS AI check on the intelligence model, not every direct assist call.

**Smallest safe fix / exit:** Require explicit approved provider/model policy, consistent user disclosure/consent decision and atomic account/global reservations across direct/queued calls. Enforce HTTPS/approved endpoint policy at the runtime boundary; record safe accepted/failed/unknown usage states without replaying ambiguous paid calls. Preserve manual writing and review UX. Verify concurrent budget exhaustion and privacy disclosure with fakes, then separately authorize vendor cost/retention acceptance.

### S-10 — Secondary resilience/integrity gaps (P2; SEC-12/14/15)

- **SMS unknown outcome:** `API/routes/auth-sms.ts:59-113` persists a receipt before send; any existing non-accepted receipt returns pending, including definite rejection/crash-before-send. `auth-cleanup.ts:8-11` expires accepted receipts only. Add durable definite-failure/unknown states and safe reconciliation; never blind-retry a possibly delivered OTP. The outbound URL contains phone/OTP parameters, requiring vendor/proxy log minimization proof, not an assertion that leakage occurred.
- **Device binding asymmetry:** Supabase `auth-sessions.ts:387-501` does not compare the stored device hash while reading a session. Define the intended binding guarantee before adding a non-destructive check; a cookie is not hardware binding. Native in-flight revocation guarantees remain unproved, including separate notification count/list snapshots.
- **Asset invariants:** `DB/community-assets.ts:18-26` still lacks status/size/type/path-uniqueness constraints; the new cleanup-table checks do not validate all asset rows. Propose focused constraints only after authorized data inspection and negative SQL fixtures, not blind normalization or migration against existing data.

## Smallest safe remediation sequence

1. **Freeze the intended release scope and acceptance owners.** Preserve all existing product behavior by default; record any temporary containment as an explicit owner-approved limitation, not a silent feature removal. No existing deployment flags are changed by this report. Do not approve enabled upload/Git/identity surfaces while their P1 gates remain unmet.
2. **Keep the two completed fixes and regression evidence.** Retain the deletion outbox and notification current-access filtering; do not reimplement SEC-03/13 from the stale audit. Complete native/storage acceptance of the existing outbox on separately approved disposable targets.
3. **Close image ingress and promotion as a narrow lifecycle change.** Bound ingress first; persist upload-time targets/capacity/expiry and stable promotion intent; add bounded decode/canonicalization before activation; then implement staged/abandoned cleanup and reconciliation. Use the existing SQL/outbox conventions and generation/lease fencing. Add failure/crash regressions before each production change.
4. **Add Git allocation/tombstones before enabling destructive cleanup.** Capture targets before cascade, retain capacity until acknowledged deletion, and validate coordinated exclusion. Keep historical orphan inventory read-only pending approval. GC/legacy cleanup is a separate reviewed operation with retained-reference restore proof.
5. **Close credential lifecycle in parallel with storage, but not via an auth rewrite.** Approve the security-event revocation policy; add minimal durable invalidation/progress; cover partial external failures and native races. Complete the selected provider's factor/bootstrap flows and only then refactor provider I/O with version fencing.
6. **Implement privacy/retention on the now-durable lifecycles.** Export/deletion/ownership and publication decisions must compose provider, object and Git state, not just delete SQL. Align direct AI controls and SMS unknown-outcome handling with approved disclosure/spending/retention policy.
7. **Release only after exact-artifact deployment proof.** Fresh source-bound tests/build, isolated native concurrency, actual provider/storage acceptance, complete package/worker supervision, target grants/schema/TLS, aggregate paging and paired restore must be recorded separately. Parent owns checkpoints, commits and any request for deployment authorization.

**Stop conditions:** no production/live DB tests, provider charges, secret inspection/rotation, hosted DDL, credential issuance, orphan deletion, GC, privacy erasure or deployment follows from this register. Source fixes may proceed only in their separately assigned scope; external actions require an explicit target and approval. Other historical findings not revalidated here remain neither closed nor newly confirmed by omission.
